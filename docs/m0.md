# M0 implementation and board handoff

Implemented on 2026-11-06; physical qualification is pending. The build targets
only Zero W v1.1, BCM2835 / ARM1176, ARM state, soft float, `RASPPI=1`.
No Circle sources were consulted. There is no OS loader or public syscall ABI yet.

The default build ID is a 12-digit SHA-256 prefix of the original build inputs.
Override it with `make BUILD_ID=my-id`; the manifest and panel use the same ID.

Run from the repository root (no git operations are used):

```sh
make
make test
make boot
python3 scripts/usb_kernel.py /dev/cu.usbmodemXXXX info
python3 scripts/usb_kernel.py /dev/cu.usbmodemXXXX tail
python3 scripts/usb_kernel.py /dev/cu.usbmodemXXXX send build/runtime.ski
```

`make boot` fetches the four pinned vendor files, verifies their hashes, assembles
`build/boot/`, and creates `build/sandbox-m0.img` plus its exact sector layout in
`build/sandbox-m0.layout.json`. It never writes a device. Claude handles flashing.
Use the complete generated image for first tests: arbitrary copying to a mounted
FAT volume can put control copies too close together. Reassembling resets the
slots to the initial confirmed generation. Do not replace only the runtime file
without regenerating its manifest and control records.

The sparse image is 135,266,304 bytes (129 MiB logical), with an MBR and one 128 MiB
FAT32 partition, type 0x0c, at LBA 2048. Sectors and clusters are 512 bytes; reserved
sectors 32; two FATs of 2048 sectors each; root starts at cluster 2. FSInfo records the computed free-cluster count and next free cluster. No partition 2/3 is used in this M0 variant. The image records
the hashes and locations of every shipped boot file. Long-name entries preserve
`LICENCE.broadcom`; firmware needs no DTB because `device_tree=` is empty.

The fixed selector is `kernel.img`, loaded by firmware at `0x8000`. Runtime
payloads load and enter at `0x100000`; their 256-byte manifest is immediately
before that address while being verified. Selector private data/stacks end below
`0x70000`, the handoff occupies 32 bytes at `0x7000`, and mailbox messages use
`0x80000`. Firmware ARM-memory query must report a zero-based region of at least
128 MiB. M0 maps only its first 128 MiB and the BCM2835 peripheral window. RAM
outside that reservation is untouched. The first 1 MiB is uncached; remaining
mapped RAM is write-through. Peripheral sections are device/XN. Domain 0 is
client, AP grants privileged access only. M1 must replace the identity map and
privileged RWX RAM with the protected user/kernel page layout before user code.

Vectors, IRQ/FIQ/abort/undefined/SVC stacks and BSS initialization are original
ARMv6 assembly. Timer compare 1 produces 10 ms interrupts. UART0 uses GPIO14/15,
115200 8N1, with a firmware-requested 3 MHz UART clock. On Zero W this deliberately
claims UART0 away from Bluetooth. The SD backend switches GPIO48–53 to ALT3 EMMC,
1-bit PIO at 25 MHz after 400 kHz initialization; it supports SD v2 SDHC/SDXC only.
No wireless driver runs. Every command/data/programming wait has a deadline;
SD waits service USB tasks and the command parser. DMA is disabled for both SD
and DWC2, so neither uses CPU cache addresses as bus addresses.

The kernel requests the Starting… image before USB, SD and timer IRQ setup.
A free-running system-timer register provides reset/BUSY deadlines even at that
stage. The starting image completes the single full `0xf7` waveform; later
images use partial `0xff` waveforms and synchronize the previous plane. The
renderer rotates the 122×250 panel to 250×122 with a 16-byte native row stride.
The font is original 3×5 glyph artwork, doubled; alphabetic glyphs share uppercase
shapes. Uptime formatting is tested against the milestone examples and changes
at most once per minute after 100 seconds. Frame comparison suppresses unchanged
images; after a refresh completes the newest state is rendered. Panel waits are
asynchronous and have a five-second BUSY deadline; SPI bytes have a 1 ms deadline.
An electrically absent panel with BUSY pulled low cannot be detected through
this write-only SPI interface. USB and UART remain the diagnostic path.

## Serialized image and control formats

All integers below are little endian. USB accepts only `kernel zero-w-armv6`;
OS/bundle and other profiles are rejected. The M0 no-OS reference is always
`0xffffffff`. Minimum transport length is 64, but a valid manifest plus aligned
ARM payload is at least 260 bytes. Maximum total transfer is 2,097,152 bytes.

Manifest version 1 is 256 bytes followed by the raw runtime payload:

| Offset | Bytes | Value |
| --- | --- | --- |
| 0 | 4 | magic `0x31494b53` (`SKI1`) |
| 4 | 4 | format 1 |
| 8 | 4 | profile 1 = Zero W ARMv6 |
| 12 | 4 | ABI `0x00010000`, M0 recovery personality |
| 16 | 4 | payload byte count |
| 20 | 4 | load address `0x00100000` |
| 24 | 4 | entry address `0x00100000` |
| 28 | 4 | zero |
| 32 | 32 | SHA-256 of payload |
| 64 | 32 | bounded ASCII build ID, NUL padded |
| 96 | 160 | zero |

There are no path names, permissions, arbitrary addresses or OS compatibility
extensions accepted in M0. Build IDs describe artifacts; they are not signatures.
Only native ARM-state recovery payloads produced for this fixed profile should
be installed. The manifest does not prove the instruction set of arbitrary raw
machine code. CRC/SHA detect corruption and provide no authenticity.

Four preallocated FAT root files are mandatory: `KERNA.BIN`, `KERNB.BIN`, each
2 MiB, and `BOOTCT0.BIN`, `BOOTCT1.BIN`, each 4096 bytes. Only the first sector of
each control file holds metadata. Their head sectors must be at least eight
sectors apart; the builder separates them by a complete slot. Both FAT copies,
partition geometry, finite cluster chains, file lengths, and file-sector overlap
are checked before enabling writes. This is a restricted original FAT32 writer,
not FatFs; it never allocates clusters or modifies FAT/directory sectors. Assets
remain read only. A physically failing card can still lose unrelated sectors.

The control record is exactly 128 words (512 bytes):

| Word | Meaning |
| --- | --- |
| 0–2 | magic `0x31434b53`, format 1, increasing record sequence |
| 3–5 | confirmed slot (0/1), pending slot (0/1/none), attempt consumed (0/1) |
| 6–8 | confirmed generation, pending generation, no-OS sentinel |
| 9–15 | zero |
| 16–23 | SHA-256 of complete confirmed manifest+payload |
| 24–31 | SHA-256 of complete pending manifest+payload, zero when absent |
| 32–126 | zero |
| 127 | ISO-HDLC CRC32 of bytes 0–507 |

Sequence/generation wrap is rejected. Initially both copies contain identical
sequence 1, confirmed A generation 1, no pending, no OS. Every transition writes
the older control copy, waits for card READY_FOR_DATA/TRAN state through CMD13,
and reads back the complete record before acknowledging it. The previous valid
copy remains intact. The newest valid sequence is authoritative; equal-sequence
but different records are rejected. Redundancy means alternating generations,
not overwriting both copies for every commit.

PUT2 replies READY before any hashing, display or storage work. RAM receives
at most 1024 bytes between cumulative ACKs. The final block receives VERIFY,
then validation starts after that reply drains. Logs are bounded, use a `LOG `
prefix and are suppressed throughout the transfer/installation. Overflow drops
logs rather than blocking. INFO reports enumeration separately from an open DTR
reader, capacities, generations, feature state, and 120-second install deadline.
The sender retries INFO up to five times and tolerates delayed INFO replies.
Fifteen-second inactivity, DTR close, suspend/unmount and bus reset cancel RAM
reception. Once installation starts it may finish despite disconnection.

The installer verifies RAM CRC and payload SHA, writes only the inactive data
sectors, waits for card programming completion, compares every sector by readback,
then commits a pending hash/generation. Trailing input is rejected before commit.
The final OK is queued after commit and reboot follows after 500 ms. If the reply
is lost, the tool exits with an explicitly unknown result and instructs the
operator to reconnect and run INFO. It never repeats PUT2 automatically. A commit
readback failure locks further updates; card-reader inspection or reboot is
needed before deciding whether the record reached media.

The selector checks the complete slot hash and **commits consumed=1 before trial
entry**. A consumed trial selects the previous confirmed slot on the next boot. A pending
slot that fails validation also falls back; the confirmed runtime clears the
abandoned pending reference before allowing another update.
Runtime confirms only the matching trial generation after 30 seconds of timer,
dispatcher, USB-task/valid-idle and storage progress. It verifies the confirmed
fallback at initialization. Watchdog feed follows dispatcher/timer progress;
blocking SD steps have bounded waits. The eight-second hardware watchdog covers
startup and TinyUSB controller waits too; upstream DWC2 has tight hardware waits
that cannot return an independent timeout. A fault there requires watchdog reset,
not an in-place USB controller recovery. This is a board qualification limitation.

If both records fail, the selector may boot a manifest-verified slot into an
unconfirmed recovery console; updates stay locked because no verified confirmed
reference exists. If neither slot validates, it prints a UART rescue message and
halts. Selector CDC rescue is not implemented. Restore the generated card image
with a card reader. A failed confirmed hash likewise requires card-reader rescue.

## Board validation still required

No physical result is claimed. Run every M0 acceptance test in milestones.md.
Capture UART from a 3.3 V adapter (GPIO14 TX, GPIO15 RX, common ground) and connect
the Mac data cable to the Zero's USB data socket. Temporary VID:PID is
`cafe:4011`, an unallocated development placeholder; serial is `M0-development`.
Do not distribute these IDs as assigned production identity.

Measure ten cold boots, reset causes, slot IDs, UART/USB/first refresh timing,
panel orientation/current+previous planes, BUSY-stuck and missing-panel behavior,
USB reset and terminal/reconnect behavior, slow-reader drops, transfer boundaries,
maximum-size installation, CRC/SHA/profile rejection, watchdog expiry before and
after runtime entry, fallback/30-second confirmation, lost final replies, corrupt
control records and slots, and repeated power cuts on two card models. In
particular qualify EMMC pin switching on the Zero W, firmware mailbox power and
clock values, SD programming completion, panel reset/partial waveform behavior,
and that the watchdog remains armed across the selector/runtime handoff. These
checks gate M0 acceptance; host tests do not establish power-loss durability.

## First board boot (2026-11-07): findings and changes

What the board showed: the selector ran `store_init()` and handed off. The runtime
then showed `USB: unavailable` and `SD/FAT unavailable`, and the text was upside
down. Nothing could be run on the board by the author of these changes, so the
cause below is a diagnosis from the code, not a confirmed one.

Both runtime failures begin with a mailbox property call made after `mmu_init()`
(`usb_init` power-on, `sd_init` power-on), while the selector made the same calls
with the MMU off. Changes:

- `property()` (`drivers/bcm2835.c`) now hands the GPU the `0xC0000000` alias
  (uncached, no GPU L2) instead of `0x40000000`, drains the write buffer before
  posting, discards stale replies, ignores replies for other messages, and retries
  three times. `property_fail` names the reason (`MBOX FULL`, `MBOX TIMEOUT`,
  `MBOX RESP`, `MBOX TAG`).
- `sd_init()` (`drivers/sd.c`) restarts from the state the selector leaves (card
  selected, 25 MHz clock running): it stops the SD clock, resets the host, waits for
  74 clocks, sends CMD0 twice, and retries the whole sequence three times.
  Each early failure sets `sd_fail` to its own code: `SD POWER`, `SD RESET`,
  `SD CLKRATE`, `SD CLOCK`, `SD CMD0`, `SD CMD8`, `SD CMD8 ECHO`, `SD CMD55`,
  `SD ACMD41`, `SD ACMD41 BUSY`, `SD NOT SDHC`, `SD CMD2`, `SD CMD3`, `SD RCA`,
  `SD CMD9`, `SD CSD VER`, `SD CSD SIZE`, `SD CMD7`, `SD CMD7 BUSY`, `SD CLOCK25`.
- `store_init()` (`core/store.c`) sets `store_fail`: the SD code above, or `SD READ0`,
  `MBR SIG`, `MBR TYPE`, `MBR RANGE`, `SD READ BPB`, `BPB`, `BPB GEOM`,
  `BPB CLUSTERS`, `DIR ...`, `FILE ...`, `CTRL ...`.
- Diagnostics: the runtime puts the store code on the panel's `Error:` line and logs
  it (plus `property_fail`) on UART and USB. The `USB:` line reads `USB POWER` or
  `TUSB INIT` when USB init fails. The selector prints the code on UART.
- Rotation: `PANEL_ROTATE_180` (default 1, `make PANEL_ROTATE_180=0` for the old
  mapping) in `drivers/panel.c`; both refresh paths draw from the one plane.

If the board still fails, read the panel: `USB POWER` with `MBOX ...` in the log means
the mailbox is the cause; an `SD ...` code names the card step.

### Second board boot (build 5ca68d431228): result and changes

Result: text right side up. Panel showed `USB: USB POWER` and `Error: SD ACMD41 BUSY`.
The mailbox works after the MMU is on (SD POWER and SD CLKRATE passed). The card
answers CMD0/CMD8/CMD55/ACMD41 but stays busy for 1.5 s after the selector used it.

- The selector now passes the card's state to the runtime in a second block at
  `0x7040` (8 words: magic, RCA, sector count, high-capacity flag, EMMC CONTROL1,
  CRC32). The runtime adopts it (`sd_adopt`): no re-initialization, only CMD13 that
  must report transfer state with the SD clock running.
- If adoption fails, the runtime power-cycles the card (property 0x28001 off, 100 ms,
  on, 50 ms) and runs the full init; ACMD41 now gets 2 s. A cold-start init in the
  selector is unchanged on the first attempt; later attempts power-cycle.
- Failure codes added: `SD NOHAND`, `SD HOSTCLK`, `SD CMD13`, `SD NOTRAN`, `SD POWER OFF`.
- Power-tag mailbox calls (0x28001) wait up to 1 s instead of 100 ms. A failed USB
  power-on shows its reason on the USB line, such as `USB POWER MBOX TIMEOUT`.

### Panel font (third change)

The 3x5 font was hard to read (A looked like B, M like H, spaces like dots). `core/render.c`
now holds an original 5x7 font drawn at 2x (12 px advance, 14 px word gap), uppercase
only, with a box for unknown characters. The status lines are `SANDBOX-KERNEL`, the build
ID, `UP:`, `USB:` and `ERR:`; long values wrap at word boundaries under their label.
`scripts/render_screen.py OUTDIR [--rotate 0|1]` compiles the same renderer on the host
and writes PNGs of the starting, error, normal and long-error screens for review before
flashing.

`UP:`, `USB:` and `ERR:` below. Both go through the same rotation as the text.
