# M1: framebuffer, assets, SDK, User mode and OS loading

Slice 1 (framebuffer, read-only assets, SDK skeleton), slice 2 (User mode,
ELF loading, system calls, the first OS program and the restart policy) and
slice 3 (input events, directory listing, the health heartbeat) are recorded
below. [Slice 2](#slice-2-user-mode-elf-loading-and-the-first-os-program)
follows slice 1; [slice 3](#slice-3-input-events-directories-and-the-heartbeat)
follows slice 2.

## Slice 1: framebuffer, read-only assets and the SDK skeleton

Built and board-tested on 2026-11-07 on the Zero W v1.1 (runtime build
`952497484ef3`, confirmed as generation 8 after its 30-second trial). This is the
first part of [M1](milestones.md#m1-framebuffer-sdfat-protected-os-loading-and-input).
No OS program is loaded yet: there is no User mode, ELF loader or syscall dispatch.

### What is built

**Mailbox.** `property_message()` (`drivers/bcm2835.c`) posts a whole tag message
through the same `0xC0000000` uncached alias, stale-reply drain and per-call timeout
as the M0 fixes; the single-tag `property()` now builds on it, unchanged in behavior.

**HDMI framebuffer** (`core/fb.c`, `drivers/fb_hw.c`). One message sets the physical
and virtual size (640x480 at first; 960x540 since 2026-11-07, below), offset, 32-bit depth and BGR pixel order (see "HDMI colors" below), allocates with
16-byte alignment and reads the pitch. `fb_parse()` accepts the reply only if every
tag answered, sizes agree, depth is 32, the pitch fits the width, the buffer is large
enough, and its ARM address lies between 128 MiB and 512 MiB. Failures are short
codes: `FB MBOX <mailbox code>`, `FB RESP`, `FB TAG`, `FB SIZE`, `FB DEPTH`,
`FB PITCH`, `FB ALLOC`, `FB BYTES`, `FB RANGE`, `FB MAP`. The buffer is mapped as
privileged, non-cacheable, execute-never sections (`mmu_map_uncached`, which refuses
the kernel's own 128 MiB and any section already mapped differently). The test
pattern is eight color bars (white, yellow, cyan, green, magenta, red, blue, black)
over a 16-step gray ramp, inside a 4-pixel white border. If the firmware keeps RGB order the bars are
swapped so they read the same. A failure is logged and never fatal; the panel
and USB are not touched.

**Read-only FAT32 assets** (`include/assets.h`, `core/assets.c`). `asset_mount`,
`asset_open`, `asset_read`, `asset_readdir`, `asset_size` and `asset_close` over the
card's first partition. It parses the MBR and BPB itself and never writes; the A/B
store (`core/store.c`) is untouched. Rules:

- Paths are absolute, at most 255 bytes, at most 16 components, no NUL, no `.` or
  `..`, no empty components; one trailing slash names a directory. Matching is on
  short 8.3 names, case-insensitive. A name only a long-name entry could hold gives
  `-ENOENT`; long-name, deleted and volume-label entries are skipped.
- Open flags other than read-only give `-EROFS` (write bits) or `-EINVAL`.
- Eight handles; each id carries a generation, so a closed or remounted handle is
  `-EBADF`, never a different file.
- Reads are at most 1 MiB (the ABI limit); files at most 64 MiB in this slice. A
  file's FAT chain is walked at open and must hold exactly the clusters its size
  needs (`FAT SHORT`, `FAT LONG`, which also catches loops). Free, bad and
  out-of-range links are `FAT FREE` / `FAT BAD`. Directory walks stop after the
  FAT maximum of 65,536 entries (`DIR LOOP`); reserved attribute bits and control
  bytes in names are `DIR ATTR` / `DIR NAME`. Every sector read is checked against
  the partition bounds. Corruption found after some bytes were read returns the
  short count; the next read returns `-EIO`.
- `asset_fail` names the failing step for logs.

**Boot probe** (`core/probe.c`). After the store starts, the runtime lists the root,
reads `/MIT.TXT` in 4 KiB chunks with a CRC-32, and opens a missing file. The probe
lines and the framebuffer lines are kept and sent again ("BOOT ...") 1 s after each
USB reader opens, because a host can miss lines sent as its port opens.

**SDK skeleton** (`sdk/`). `sandbox/abi.h` declares the draft 1.0 call numbers,
errors, open flags, ioctl IDs and the records for `open`, `read`/`write`, `close`,
`ioctl`, `exit`, framebuffer query and present, each with size and offset asserts.
`sandbox/syscall.h` has ARM-state `svc #0` wrappers, including `sbx_log` (a write to
an open `/dev/log`). The kernel declares the same records separately in
`include/abi.h`; `tests/abi_layout.c` proves both agree field by field on the host
and on ARM32. `abi_check()` (`core/abi.c`) applies the header rules: ABI major,
record size equal to the register size and at least the minimum, 8-byte alignment,
zero flags and reserved words, and zero bytes past what the kernel knows.

## Slice 2: User mode, ELF loading and the first OS program

Built and board-tested on 2026-11-07 on the Zero W v1.1 (generations 9 to 12,
each confirmed after its 30-second trial; the branch head is generation 12). The
card's `/OS` now holds DIAG.ELF, a test copy TDIAG.ELF and the seven fault programs. This covers acceptance tests 2, 3, 4 and
5 in a first form; the gaps are listed under Next.

### Address space

`core/uspace.c`. The privileged table is still M0's identity map (first 128 MiB of
RAM, AP=01, so User mode has no access; MMIO device and execute-never). The user
table is a copy of it plus 4 KiB pages from a 16 MiB pool at physical 64 MiB, inside
kernel RAM (the link map asserts the kernel ends below it). ARMv6 extended small
pages: text is APX=1 AP=10 (read-only for both modes) and executable; read-only
data adds XN; writable data, the stack and the framebuffer surface are AP=11 and
always XN; a writable and executable mapping is refused. User ranges, inside the
design's reservations:

| Virtual range | Use |
| --- | --- |
| `0x08000000–0x0fffffff` | ELF segments (8 MiB quota); below it the kernel map, privileged only |
| `0x40000000` | `/dev/fb0` surface, once mapped |
| `0x6ffff000` | read-only startup record (`sbx_startup`), address in r0 at entry |
| `0x7fef0000–0x7ffeffff` | 1 MiB stack; the page below is unmapped (guard) |
| `0x0000f000` | lr at entry: returning there is an exit with r0 as status |

The kernel does not yet live at `0x80000000`; moving it high is later work. Because
the user image window now sits at 128–256 MiB, `mmu_map_uncached` accepts a
framebuffer only from 256 MiB up (the firmware gave 0x1eace000). The kernel never
dereferences a user address: `us_span`/`us_check` translate through the region
list, check write permission, and refuse wraparound, nonzero upper bits and the
kernel half (`EFAULT`).

### Entry, exceptions and the supervisor

`user_enter` (`arch/armv6/start.S`) saves the kernel's registers, switches TTBR0 to
the user table, invalidates the TLB and branch predictor and returns into User mode.
Every exception taken from User mode (svc, IRQ, undefined, prefetch and data abort)
saves r0–r12, sp, lr, pc and cpsr into the frame, switches back to the privileged
table and returns from `user_enter` with a reason; the same exceptions from a
privileged mode still panic as in M0. An IRQ is left pending and taken in SVC mode
once the kernel unmasks interrupts, so the timer and USB are serviced normally.

`core/os.c` runs the program one slice at a time from the kernel main loop. USB,
the panel, the watchdog feed and the trial check keep running between slices; the
10 ms timer ends every slice. Policy (first form, no OS A/B pair yet):

- A clean `exit(0)` or a return of 0 from the entry point: "OS exit 0", recovery
  console; the program's last frame stays on HDMI.
- A fault (undefined instruction, prefetch or data abort, Thumb state, no system
  call for 2 s) or a nonzero exit: logged with pc, fault status and address, handles
  and the surface are revoked, the kernel's own HDMI screen is drawn again, and the
  program is restarted once. A second fault within 60 s stops it: "OS stopped;
  kernel recovery console kept". A RUN request starts a fresh budget.
- The OS program starts 10 s after boot, so a program that could take the kernel
  down can be replaced over USB first; a RUN (or any USB command still in progress)
  during those 10 s takes over. It was `/OS/DIAG.ELF` alone until 2026-11-07; now
  (`core/autostart.c`) the kernel starts `/OS/GMOS.ELF` when it is on the card, else
  `/OS/DIAG.ELF`, and says which at boot: "OS autostart in 10 s: /OS/GMOS.ELF".
  - `/OS/AUTORUN.TXT` (optional; the card is read with 8.3 names, so not
    AUTOSTART.TXT) overrides that order. Its first line names a program in `/OS`:
    1 to 8 of `A-Z 0-9 _ -`, then `.ELF` (any case, surrounding blanks and CR
    ignored; later lines are free for notes). A choice that is invalid or not on
    the card is logged ("... ignored") and the default order applies. It can be
    sent like any `/OS` file (`usb_kernel.py put AUTORUN.TXT`) and replaced the
    same way; the kernel cannot delete files, so a line such as `GMOS.ELF` (or a
    blank one, which is ignored) goes back to the default order.
  - A chosen program the loader rejects ("OS reject <path> <code>") gives way to
    `/OS/DIAG.ELF` at once. When the autostarted program faults twice within 60 s
    (the restart policy above gives up), the kernel starts `/OS/DIAG.ELF` instead
    and reports "OS fell back to DIAG.ELF after repeated faults" in the log and as
    the status panel's last error; the HDMI screen shows the diagnostics pattern.
    DIAG itself faulting twice keeps the recovery console, as does a program
    started by USB RUN (no fallback for those). A missing DIAG.ELF keeps the
    recovery console ("OS none; recovery console").

The 2-second rule is the heartbeat in its first form: any system call counts as
progress. The design's `health` call and readiness report come later.

### ELF checks

`core/elf.c`, acceptance test 3. Accepted: little-endian ELF32, `ET_EXEC`, `EM_ARM`,
EABI version 5 with only the soft-float flag, header sizes 52/32, 1–16 program
headers inside the file, at most 4 non-empty `PT_LOAD` segments, files up to 1 MiB.
Each segment: flags only R/W/X and never W+X, `filesz <= memsz`, file range inside
the file, power-of-two alignment congruent with the offset, entirely inside the
image window, no page shared with another segment, total pages within the 8 MiB
quota. The entry is 4-byte aligned (bit 0 set is "ELF THUMB") and inside an
executable segment's file bytes. Rejected program headers: `PT_INTERP`,
`PT_DYNAMIC` (runtime relocations, imports), `PT_SHLIB`, `PT_TLS`, an executable
`PT_GNU_STACK`, and any unknown type. If a section table is present it must be in
bounds and hold no allocated `REL`, `RELA`, `DYNAMIC`, `DYNSYM`, `HASH` or
`GNU_HASH` section. Not yet checked: the `.ARM.attributes` contents (CPU
architecture, VFP use).

### System calls

`core/sys.c`, acceptance test 4. r7 is the call; r3–r6 must be zero (`EINVAL`), r2
the ABI major (`EPROTONOSUPPORT`), r0 an 8-byte aligned record readable by the
program (`EFAULT`), r1 its size (16–4096 bytes, a multiple of 8). The record is
copied in, `abi_check`ed against the published size, its output fields must be zero,
and a record with outputs must be writable. Outputs are copied back only on
success. Calls: `open` (1), `read` (2), `write` (3), `close` (4), `ioctl` (5), `mmap`
(6, new: only the `/dev/fb0` surface, read/write and shared) and `exit` (16); the
rest are `ENOSYS`, as is `svc` with a nonzero number.

- `/sd/...` opens the slice-1 asset reader read-only (`/sd` is the root
  directory); write flags are `EROFS`. `/dev/log` is write-only; each write logs
  one line of up to 120 characters as `OS: ...`. `/dev/fb0` is one handle at a time.
- 16 handles per program; ids carry a generation, so a closed or stale id is
  `EBADF`. Transfers over 1 MiB are `EINVAL`; reads go straight into the checked
  user pages.
- Framebuffer: query returns 640x480, pitch 2560, format XRGB8888 and the surface
  size; a smaller record is `EINVAL`. `mmap` maps the surface at `0x40000000`.
  Present copies a bounds-checked rectangle to the HDMI buffer (pitch and pixel order
  handled); the kernel logs a CRC of what reached the screen when the program ends.
- Modes (ABI 1.2, 2026-11-07, `docs/js-spike.md`): ioctl `0x10002` (`sbx_fb_set_rec`:
  width, a multiple of 4, height and format 1 XRGB8888, 2 RGB565 or 3 8-bit indices)
  asks the firmware for another buffer, which it scales to the HDMI mode; the mode must
  fit in the program's 1,228,800-byte surface (960x540 at 16 bpp does, 1920x1080 does
  not). Query then reports the mode, its pitch (width x bytes a pixel) and format.
  Present copies the bytes as they are at 16 and 8 bpp. Ioctl `0x10003`
  (`sbx_fb_palette_rec`) sets palette entries (0x00RRGGBB) for 8 bpp. The kernel logs
  "FB mode WxHxD in N us". 640x480x32 stays the mode every program starts in.
- The kernel's own screen (2026-11-07): the boot test pattern is 960x540x32, half of
  1080p, so a 1080p monitor (the boot config now forces CEA mode 16 with
  `scaling_kernel=8`, nearest-neighbor) shows it doubled, edge to edge, with no
  black bars. Starting a program sets 640x480x32 first (about 4 ms, logged as an
  `FB mode` line; if the firmware refuses, the screen is given up rather than let a
  program write past its surface). A fault puts the 960x540 pattern back; a clean exit
  leaves the program's last frame up in its own mode (DIAG's tiles stay on screen)
  until the next program starts. DIAG draws its tiles at 960x540x16 (60-pixel tiles)
  when the kernel has ABI 1.2 and logs `DIAG fb 960x540x16 presented, crc N`; with an
  older kernel it draws 640x480x32 as before.

### USB: PUTF and RUN

The card had no way to receive a file other than a runtime, so the protocol gained
two development commands (`core/protocol.c`, `core/fatput.c`):

- `PUTF <NAME> <size> <crc32> <sha256>`: 1 byte to 1 MiB (512 KiB until 2026-11-07; now the ELF loader's own limit, so a JS runtime fits), sent in 1024-byte blocks
  like `PUT2`, checked by CRC-32 and SHA-256, then written as `/OS/<NAME>` (or
  `/GAMES/<DIR>/<NAME>`, or from 2026-11-07 `/OS/APPS/<DIR>/<NAME>` for `APPS/<DIR>/<NAME>`:
  an app's folder, `usb_kernel.py putapp <folder> <DIR>`). Names are
  upper-case 8.3 only; nothing outside `/OS` changes except the one root entry that
  creates `/OS`. Not during a pending kernel trial or while a program runs. Data is
  written first, then the FAT chain in both copies, then the directory entry, then
  the old chain is freed and the FSInfo free count adjusted; every sector is read
  back, and writes outside the FAT and data areas are refused. A power cut can leak
  clusters, never cross-link or truncate a file. The first board attempt showed the
  free-cluster scan reading the FAT once per cluster, past the 8 s watchdog (the
  board reset before writing anything); it now reads each FAT sector once, with a
  host test bounding the reads.
- `RUN <NAME>` starts `/OS/<NAME>`.
- `scripts/usb_kernel.py <port> put <file> [--name NAME]` and `run <NAME>`.

## Slice 3: input events, directories and the heartbeat

Built and board-tested on 2026-11-07 on the Zero W v1.1 (generation 13, then
generation 14 with the folder-growth fix below; both confirmed after their
30-second trials; the branch head is generation 14). It covers acceptance test 8
with a synthetic source, the heartbeat part of test 5, and what the first
Game-Maker OS program needed: a directory listing.

### Input events

`core/input.c`, `/dev/input/event0` (the path the design names; the device tree
uses `/dev/input/eventN`). Records are the design's 16 bytes: `u64` monotonic
nanoseconds, `u16` type, `u16` code, `i32` value, with Linux input numbering
(`EV_SYN` 0, `EV_KEY` 1, `EV_ABS` 3, `SYN_REPORT` 0, `SYN_DROPPED` 3).

- **Source.** The only source is synthetic and says so: the query flag
  `SBX_INPUT_SYNTHETIC` is set, and the boot log reads
  `INPUT /dev/input/event0 synthetic (USB KEY, AXIS)`. The board has no buttons
  and the e-ink HAT has none, so there is no GPIO source.
- **Frames.** A source reports up to 16 changes at once; the queue adds them
  with one shared timestamp and closes them with `SYN_REPORT`. Keys are codes
  1–767 with values 0 (up), 1 (down) or 2 (repeat); axes are codes 0–31 with
  values −32768 to 32767. As in the Linux input core, a change that changes
  nothing is dropped (a second press, a release of a released key, a repeat of a
  key that is up, an axis at the same value), and a frame left empty adds no
  `SYN_REPORT`. A bad change refuses the whole frame (`EINVAL`) and changes
  nothing.
- **Reading.** Open read-only with `O_NONBLOCK` (a blocking open is `EINVAL`
  until `poll` exists; a write open is `EACCES`); one reader at a time (`EBUSY`).
  A read returns whole records only (fewer than 16 bytes is `EINVAL`), at most
  16 per call, and `EAGAIN` when the queue is empty. The queue holds 64 records.
- **Overflow.** A frame that does not fit empties the queue and leaves one
  `SYN_DROPPED`; the frame itself is not queued, but its changes are in the
  state. Later frames queue after the `SYN_DROPPED` as usual.
- **Resynchronizing.** `ioctl` 0x30001 returns the current state (768 key bits,
  32 axes) and empties the queue, as Linux's state queries do, so a change is
  never seen twice. A reader does this after `SYN_DROPPED`, and may do it after
  opening (frames that arrive with no reader change only the state).
- **Query.** `ioctl` 0x30000: flags, instance, queue records (64), keys (768),
  axes (32), axis minimum and maximum.
- **Removal.** `INPUT remove` ends every open handle: reads and queries are
  `ENODEV`, and so are opens and new frames until `INPUT add`. An added device is
  a new instance with a cleared state; a handle from before stays `ENODEV`.
- Records and constants are in `sdk/include/sandbox/abi.h` (`sbx_input_event`,
  `sbx_input_info`, `sbx_input_state`), checked against the kernel's by
  `tests/abi_layout.c` on the host and on ARM32.

### USB input commands

`core/protocol.c`, after `INFO` like the other development commands:
`KEY <code> <down|up|repeat>`, `AXIS <code> <value>` and `INPUT <add|remove>`.
Each `KEY` or `AXIS` is one frame. Replies are `OK key 103 down`,
`OK axis 0 -32768`, `OK input remove`, or `ERR input command|value|range|no-device`.
`scripts/usb_kernel.py <port> key up down enter esc` presses and releases keys by
name or code (`enter:down` sends only the press); `axis` and `input` send the
other two.

### Directories

`getdents` (call 11, the read record's layout): whole entries
`{u16 length, u8 type, u8 name bytes, u32 size}`, then the 8.3 name and zero
padding to a multiple of 8. Types are file 1 and directory 2; `.` and `..` are
left out. An entry that does not fit waits for the next call, and a buffer too
small for it is `EINVAL`. A file handle or a device is `ENOTDIR`; `read` on a
directory stays `EINVAL`.

### Health heartbeat

`health` (call 17): `{generation, sequence}`. The generation must be the boot
generation and the sequence must rise (from 1), or the call is `EINVAL` and does
not count. The first accepted call is the readiness report (`OS ready <path>
after <n> ms`) and must come within 10 s of the start; after it a call must come
at least every 2 s. Missing either is a fault (`no readiness report in 10 s`,
`heartbeat missed 2 s`) with the usual restart policy. Other calls no longer
count as progress: this replaces slice 2's 2-second no-call rule. The check runs
on every return to the kernel, timer slice or call, so a program making only
other calls is stopped too. DIAG reports readiness after its greeting; LOOP now
reports once and then loops. A program blocked inside the kernel would need the
deadline paused; nothing blocks yet.

### PUTF into game folders

`PUTF GAMES/<DIR>/<NAME> ...` installs a development file as
`/GAMES/<DIR>/<NAME>` (8.3 names, upper case; `DIR` without an extension),
creating `/GAMES` and the folder when missing. Every other rule of `PUTF` holds:
same checks, write order and readback; the root changes only to add `OS` or
`GAMES`. `scripts/usb_kernel.py <port> putgame <folder> <DIR>` sends every file
of a folder. The first board copy stopped with `PUT DIR FULL` after 18 files: a
folder never grew past its first directory cluster. A full folder (never the
root) now gains a zeroed cluster at the end of its chain, written and marked
end-of-chain before it is linked, so a power cut can only leak it.

From 2026-11-07 a game packed in one file goes the same way: `PUTF
GAMES/<NAME>.GMP` or `PUTF POCKET/<NAME>.GMP` (the Pocket Player's folder, so one
card serves both players; further volumes of a split pack are `<NAME>.G01` to
`<NAME>.G99`), and `PUTF GAMES/LIBRARY.JSL` for the library index beside them.
Those are the only files allowed directly in `/GAMES` or `/POCKET`; the root
changes only to add `POCKET` when it is missing. A pack over 1 MiB (the transfer
limit) goes on the card from a card reader.

## Slice 4: the clock and sleeping

Built and board-tested on 2026-11-07 on the Zero W v1.1 (generation 15,
confirmed after its 30-second trial). It adds the two calls Game-Maker OS needed
to play a game at a steady rate, and nothing else: ABI 1.1.

### clock_gettime and sleep_until

- **`clock_gettime`** (call 13): `{clock, ns}`, 32 bytes. Clock 0 is the only
  one: monotonic nanoseconds since the kernel started, in microsecond steps.
  It is the clock input events carry, so the two compare directly. Another
  clock, a nonzero `ns` on entry or a short record is `EINVAL`.
- **`sleep_until`** (call 14): `{deadline}`, 24 bytes, absolute monotonic
  nanoseconds. The program is not entered again until the clock reaches the
  deadline (rounded up to the next microsecond, so it never wakes early); a
  deadline already passed returns at once. The kernel loop keeps serving USB,
  the panel and the watchdog meanwhile. Waiting is not progress: the heartbeat
  deadline keeps running, so a program wakes in time to report (a sleep past it
  is the usual `heartbeat missed 2 s` fault). A stop or restart clears the
  sleep.
- `core/os.c` `os_asleep` decides, each pass of the kernel loop, whether the
  program stays asleep; `core/sys.c` holds the deadline (`sys_wake_us`).
- The SDK has `sbx_clock_rec`, `sbx_sleep_rec`, `SBX_CALL_CLOCK_GETTIME`,
  `SBX_CALL_SLEEP_UNTIL`, `SBX_CLOCK_MONOTONIC` and the wrappers `sbx_clock_ns`
  and `sbx_sleep_until`; `sbx_startup.minor` is 1. A program checks the minor
  before using them: on a 1.0 kernel both calls are `ENOSYS`.

## HDMI colors: pixel order (2026-11-07)

With HDMI forced on at 640x480, photos of the monitor showed red and blue swapped:
the Game-Maker OS games list had a maroon background where the host render is
navy, and its yellow highlight showed sky blue; the DIAG checkerboard was swapped
the same way. The boot log said `FB ok 640x480 32 2560 ... order 1`: the kernel
asked for pixel order 1 ("RGB") and the firmware accepted it.

Cause: the firmware's pixel order names the bytes in memory, lowest address first.
Order 1 stores R, G, B, X, so the little-endian word `0x00RRGGBB` that programs
write (`SBX_FB_FORMAT_XRGB8888`) and the test pattern use reached the screen with
red and blue swapped. The kernel had the meaning backwards: it treated order 1 as
the one that needs no swap.

Fix: the kernel now requests order 0 ("BGR": bytes B, G, R, X, which is the word
`0x00RRGGBB`), and `fb_native()` (`include/fb.h`) swaps red and blue only when the
firmware reports order 1. The test pattern and `FB_PRESENT` both go through it.
Programs and the ABI are unchanged: the surface stays XRGB8888 `0x00RRGGBB`, and the
color on screen is the one written. Host tests check the request asks for order 0,
that order 0 passes pixels through and that order 1 swaps them.
